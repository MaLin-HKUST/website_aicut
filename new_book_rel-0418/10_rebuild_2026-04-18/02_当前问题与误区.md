# 02. 当前问题与误区

本文回答什么问题：

- 今天线上混乱的根本原因是什么
- 之前的 Agent 哪些判断是错误的
- 本轮重建时必须避免重复哪些误区

## 1. 第一类误区：把系统误判成单机网站

错误表现：

- 只盯着页面和前端样式
- 认为只要修好网站页面就等于修好了系统
- 忽略 Worker、调度、TOS 这三层

实际问题：

- `website_aicut` 是分布式任务处理系统
- 网站只是入口，不是系统全部

## 2. 第二类误区：把 A 机器当成万能运行机

错误表现：

- A 机器同时挂网站、调度、Gateway、算法验证、临时脚本、历史目录
- 遇到新需求先往 A 机器塞

实际问题：

- A 机器应该只做主服务器和调度中心
- Gateway 与算法执行应回到 Worker

## 3. 第三类误区：把当前线上临时状态当目标架构

错误表现：

- 看到 `release_0415_slot` 在跑，就把它当长期标准
- 看到旧主站容器还在，就继续依赖它
- 看到某个端口能通，就默认它该长期存在

实际问题：

- 当前线上状态是历史修补的结果
- 不是设计完成态

## 4. 第四类误区：没有先定义数据库边界

错误表现：

- 先改页面、先改 API，再倒推数据库应该怎么分工
- 对 SQLite 和 PostgreSQL 的边界没有写死

实际问题：

- SQLite 只该服务网站主服务器
- PostgreSQL 只该服务调度中心

## 5. 第五类误区：发布方式不统一

错误表现：

- 有时本地 build + scp
- 有时直接改线上目录
- 有时尝试云上 git pull + build

实际问题：

- 线上真实运行版本不容易说清
- 回滚锚点不稳定
- 一个 Agent 很难判断当前哪条线是正式线

## 6. 第六类误区：备份意识弱于修复冲动

错误表现：

- 先修服务，再想是否需要备份
- 只关心镜像，不关心数据库恢复

实际问题：

- 没有备份与恢复锚点，重建就不安全
- 这也是为什么本轮必须把数据库、release、镜像的备份策略一起定下来

## 7. 本轮重建必须记住的教训

- 页面问题不等于系统问题
- A 机器不是执行机
- 当前线上不是标准架构
- 不要在未定义边界前做局部重写
- 不要在未备份前做清洗

## 对 Agent 的直接指令

- 如果你发现自己只在讨论“页面为什么不对”，请停下来重新确认你是否忽略了系统边界。
- 如果你准备在 A 机器继续塞执行侧组件，请先回到系统定义文档重读。
- 本轮专项中，任何“先跑起来再说”的做法都需要被高度质疑。
