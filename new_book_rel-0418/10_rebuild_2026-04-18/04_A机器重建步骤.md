# 04. A 机器重建步骤

本文回答什么问题：

- A 机器应该按什么顺序清洗和重建
- 重建前必须备份什么
- 哪些东西必须保留，哪些东西可以清理

## 1. 重建前置条件

开始前必须满足：

- 已完成 SQLite 备份
- 已完成 PostgreSQL 备份
- 已完成当前 release 信息归档
- 已确认 Worker 机器的目标运行方案
- 已确认 TOS 备份空间可用

## 2. 第一步：冻结当前线上状态

目标：

- 在重建开始前固定一个可回滚基线

需要做：

- 记录当前 nginx 配置
- 记录当前 A 机器运行容器
- 记录当前关键端口
- 记录当前 SQLite 路径
- 记录当前 PostgreSQL 实例和表状态

完成标准：

- 有一份完整的“重建前快照”

## 3. 第二步：备份必须保留资产

必须备份：

- SQLite 数据文件
- PostgreSQL 逻辑备份
- 正式 release 相关镜像或 manifest
- nginx 配置
- 证书路径说明
- 当前部署脚本

补充说明：

- PostgreSQL 当前数据虽可清空，但仍建议完整导出一次，作为结构参考和回退锚点

## 4. 第三步：转移或冻结旧主站资产

目标：

- 让 A 机器清洗时不丢失 admin/SQLite 恢复能力

可选做法：

- 把旧主站 SQLite 和相关运行资产复制到备份位置
- 需要时可再迁回 A 机器

## 5. 第四步：停掉错误运行面

应停掉的对象：

- 旧主站 `3000` 正式流量角色
- 历史前端长期并存运行面
- A 机器上的 Worker 正式运行面
- 无主测试容器
- 历史验收目录的正式服务职责

注意：

- 停服务不等于立即删除
- 删除动作必须在新主链路跑通后再做

## 6. 第五步：重建 A 机器正式运行面

A 机器应按以下顺序重新建立：

1. SQLite 网站主数据层
2. 网站业务 API
3. PostgreSQL 调度库
4. 调度 API
5. Scheduler Runtime
6. 正式网站前端
7. nginx

这里的目标是把 A 机器收敛成“网站主服务器 + 调度中心”。

## 7. 第六步：重新定义路由

目标：

- 域名只对接一套正式前端
- 前端只按规则转发到两类后端

应达到：

- 网站侧接口清晰
- 调度侧接口清晰
- 不再长期存在“旧前端 + 新前端 + 旧 API + 新 API”的混搭

## 8. 第七步：新主链路验收

A 机器最低验收：

- 登录
- admin
- 网站页面打开正常
- 调度 API 健康
- Scheduler 正常
- PostgreSQL 正常

## 9. 第八步：删除历史包袱

只有在新主链路验收通过后，才进入删除阶段。

可删除对象包括：

- 无主测试容器
- 无主镜像
- 历史前端运行面
- 不再承担正式职责的旧发布目录

数据库、证书、有效回滚锚点不在此列。

## 对 Agent 的直接指令

- 先备份，再停服务，再重建，再删历史。
- 不要跳过“冻结当前状态”和“新主链路验收”这两步。
- 如果某一步无法给出回滚锚点，就不要进入下一步。
