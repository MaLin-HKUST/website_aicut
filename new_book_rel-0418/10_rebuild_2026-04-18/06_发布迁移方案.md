# 06. 发布迁移方案

本文回答什么问题：

- 当前混乱的发布方式应该如何迁移到统一发布流
- 本轮重建期间，发布应如何做才最稳
- 未来标准发布流应该是什么

## 1. 当前发布问题

当前混乱点在于：

- 本地打包上传与云上构建混用
- 线上目录被当成构建目录和运行目录混用
- 没有统一 release manifest
- 没有稳定的切流和回滚锚点

## 2. 本轮重建期间的过渡发布原则

过渡期允许：

- 先用最稳的发布方式保证重建成功

但必须逐步收敛到：

- Git 作为代码入口
- 云上拉取同一版本
- 云上统一构建
- 云上统一切换

## 3. 未来标准发布流

### 3.1 本地

- 开发
- 测试
- 提交
- 打 tag 或 release id

### 3.2 A 机器

- 拉代码
- 备份当前 release
- 构建 A 机器所需服务
- 健康检查
- 切流

### 3.3 Worker 机器

- 拉同一版本
- 构建 Gateway 与算法运行面
- 健康检查
- 接回 A 机器调度中心

## 4. 为什么不建议长期走“本地大包上传”

因为它会带来：

- 本地磁盘压力
- 大包上传时间成本
- 线上实际运行版本不透明
- 回滚锚点不清晰

## 5. 为什么本轮仍可能允许短期过渡手段

如果云上构建条件暂时不足，例如：

- 内存
- swap
- Docker builder 条件

则本轮允许使用过渡手段完成重建，但必须在文档里标记为过渡方案，而不是长期规范。

## 6. 发布脚本必须具备的能力

正式发布脚本必须包含：

- 拉代码
- 记录版本
- 当前版本备份
- 构建
- 候选服务启动
- 健康检查
- 切流
- 回滚入口

## 对 Agent 的直接指令

- 不要在本轮重建中继续发明第四种发布方法。
- 如果你暂时用了过渡方案，必须在文档中明确写出它是过渡，不是长期标准。
