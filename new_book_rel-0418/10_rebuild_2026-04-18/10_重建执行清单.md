# 10. 重建执行清单

本文回答什么问题：

- 本轮重建应该按什么清单推进
- 每一步完成后要检查什么
- 哪些任务之间存在先后依赖
- 参与重建的 Agent 到底应该按什么顺序执行
- 每一步需要什么输入、要做什么网络操作、产出什么证据

## 使用方式

本文件不是抽象原则，而是本轮重建的执行 runbook。

执行要求：

1. 先读完 `00_system_knowledge/`
2. 再读完 `10_rebuild_2026-04-18/`
3. 执行前打开 [`../基础网络信息和账号信息.md`](../基础网络信息和账号信息.md)
4. 每完成一步都要留下证据
5. 没有通过当前步骤的完成标准，不进入下一步

建议把本文件当成“主驾驶舱”，并为每一个阶段单独建立时间戳目录，例如：

- `rebuild-artifacts/20260418_pre_rebuild_snapshot/`
- `rebuild-artifacts/20260418_backup_anchor_1/`
- `rebuild-artifacts/20260418_a_machine_stable_anchor_2/`
- `rebuild-artifacts/20260418_full_chain_anchor_3/`

每个目录应至少保存：

- 运行命令
- 输出日志
- 生成的备份文件名
- SHA256
- manifest
- 验收结果

## 证据格式

每个阶段完成时，建议统一用以下格式记录证据：

- `phase`: 当前阶段编号
- `time`: 开始时间 / 结束时间
- `operator`: 执行人或执行 Agent
- `inputs`: 本阶段使用的关键输入
- `commands`: 关键命令
- `network_ops`: 涉及的 SSH / Git / TOS / 域名操作
- `artifacts`: 生成文件清单
- `verification`: 如何验证成功
- `rollback_anchor`: 当前阶段新增或沿用的回滚锚点
- `status`: passed / blocked / rolled_back

如果阶段失败，必须额外记录：

- `failure_reason`
- `last_good_anchor`
- `next_action`

## 暂停、升级与回滚规则

以下情况必须暂停，不允许继续推进：

- 当前阶段的输入不完整
- 当前阶段未生成证据
- 当前阶段没有明确回滚锚点
- 验证失败但原因未定位

以下情况必须先回滚，再继续：

- 正式流量出现不可接受故障
- SQLite 数据受到破坏风险
- nginx 切流后静态资源与 HTML 指向不同运行面
- 调度 API 或 Scheduler 启动后导致现有任务状态异常

以下情况必须升级处理，不允许由单个 Agent 自行猜测：

- A 机器与 Worker 的职责边界再次发生冲突
- SQLite 与 PostgreSQL 数据边界需要调整
- TOS 桶、前缀或访问策略需要更改
- 正式域名入口需要改变
