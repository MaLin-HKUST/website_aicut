# 07. 备份迁移方案

本文回答什么问题：

- 在正式重建前，当前系统如何先补齐备份能力
- 本轮重建期间每个阶段应有哪些回滚锚点
- 当前数据库、release、镜像应该如何迁移到 TOS 备份体系

## 1. 当前备份缺口

当前主要缺口包括：

- SQLite 缺少标准化的本地 3 天 + TOS 长期保留方案
- PostgreSQL 缺少稳定的正式备份机制
- release 缺少 manifest
- 镜像缺少分层归档策略

## 2. 本轮开始前必须先补的备份

### 2.1 SQLite

先做：

- 一份当前全量备份
- 一份校验过的压缩备份
- 一份上传到 TOS 的远端副本

### 2.2 PostgreSQL

先做：

- 一份 `pg_dump`
- 一份压缩包
- 一份上传到 TOS 的远端副本

### 2.3 release 信息

先做：

- 当前线上 release 信息归档
- 当前 nginx 和发布脚本归档

## 3. 本轮重建时的回滚锚点

建议至少保留三个锚点：

1. 重建前锚点
- 旧 A 机器线上状态快照

2. A 机器新主链路锚点
- A 机器网站与调度中心重建完成后的第一版稳定态

3. Worker 接回锚点
- Worker 侧重连调度中心并跑通主链路后的第一版稳定态

## 4. TOS 备份迁移

迁移后的策略应为：

- 本地保留最近 3 天
- 所有正式备份同时上传 TOS
- TOS 上保留长期版本

建议把备份对象分为：

- sqlite backups
- postgres backups
- release bundles
- release images

## 5. 镜像迁移策略

当前开始执行：

- 只把正式 release 镜像导出到 TOS
- 测试镜像不归档
- 历史无主镜像清理前先确认不在 release manifest 中

## 对 Agent 的直接指令

- 这一轮重建不是先删再备，而是先补齐最小备份，再动手清洗。
- 每完成一个阶段，就要新增一个回滚锚点，而不是一直只保留最初的旧系统备份。
