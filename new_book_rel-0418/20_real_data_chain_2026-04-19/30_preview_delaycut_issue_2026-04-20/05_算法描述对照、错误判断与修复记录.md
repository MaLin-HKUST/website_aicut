## 2. 本轮最终判断

### 2.1 结论

这次问题的主因不是 `script_to_delay_cuts.py` 的核心定位算法把“粗剪算法”理解错了。

这次问题的主因是：

- preview 阶段收到了一份不满足算法前提的 `edited_script`
- 系统层没有阻止这类错数据进入 preview
- 算法层又把真正的“文本未命中 ASR”误报成了“片段时长非正数”

### 2.2 更准确的责任划分

#### 算法原意没有错

根据原始算法描述，`script.txt` 的含义是：

- 基于当前任务自己的 ASR 原文
- 用 `{}` 标出要删除的内容
- 再拿这份 script 和同一个任务自己的 ASR A 对照，生成 DelayCut

也就是说，preview 阶段本质上是：

- 在“当前任务自己的 script”上调删除范围
- 不是换一份别的正文
- 更不是允许输入另一条任务的脚本

- [cujian_prd.md](</Users/malin13/Documents/trae_projects/website_aicut/doc/cujiian/cujian_prd.md:22>)

#### 当前实现的大方向其实是符合算法的

`cut_breakpoints` 里的产品/算法文档明确写了：

- 设计目标是“删除型编辑”，不是改写新稿
- `Script1.txt` 是“原始口播 + 删除标记”
- AI 只能删，不能改写

对应证据：

#### 真正偏离算法的是 preview 输入边界

当前 `website_aicut` 的 preview API 在本轮修改前存在两个问题：

1. `edited_script` 被定义成 `Any`
2. 服务端没有校验“这是不是当前任务 analyze_script 的删除线调整版”

结果就是：

- 只要有人把另一条任务的 script 文本塞进来
- preview 也会照单全收，继续调度 worker

### 2.3 这次不是哪一种问题

这次不是：

- TOS 下载错文件
- Worker Gateway 传错 stage
- DelayCut 还在用老的“按字符位置硬映射”算法

相反，`script_to_delay_cuts.py` 之前已经修过一次“Script 去掉 `{}` 后与 ASR 原文不完全一致”的场景，当前版本是按“内容搜索当前 ASR 原文”来定位，而不是按旧的固定字符位置。

证据：

因此：

- 当前 DelayCut 算法是能容忍“正常删除型编辑带来的文本差异”的
- 这次失败是因为片段在当前 ASR 里根本不存在，而不是“同任务内轻微文本差异没处理好”

## 3. 算法定义与代码对照

### 3.1 原算法定义

原算法要求：

1. 先对当前任务视频做 ASR，得到 ASR A
2. 大模型基于当前任务 ASR 生成带 `{}` 的 `script.txt`
3. preview 允许用户调删除位置
4. 再用当前任务自己的 script 和当前任务自己的 ASR A 生成 DelayCut

这意味着 preview 阶段的合法修改类型是：

- 调 `{}` 的范围
- 调保留/删除边界

不是：

- 替换正文
- 改成另一条任务的 script
- 自由重写整篇文本

### 3.2 当前代码里符合算法设计的部分

#### AI 生成 script 的约束是正确的

提示词明确要求：

- 保持 ASR 原始顺序
- 只能删，不能改写
- 所有删除必须用 `{}` 包起来

证据：

- [AI_core/prompts/system.md](/Users/malin13/Documents/trae_projects/aicut2602/libs/cut_breakpoints/AI_core/prompts/system.md:8)

#### 前端编辑器的交互也符合算法定义

当前前端编辑器只支持：

- 拖选文字
- 标记删除
- 恢复保留
- 把可见文本按选区重新加 `{}` 发回后端

它没有“直接改正文”的自由编辑逻辑。

证据：

- [script-editor.tsx](/Users/malin13/Documents/trae_projects/website_aicut/apps/web/components/smart-cut/script-editor.tsx:99)
- [smart-cut.ts](/Users/malin13/Documents/trae_projects/website_aicut/apps/web/lib/smart-cut.ts:204)

#### analyze 阶段生成初始 edit 的方式也符合算法定义

analyze 完成后会把当前任务自己的 analyze script 直接保存为第一版 edit。

证据：

- [analyze_processor.py](/Users/malin13/Documents/trae_projects/website_aicut/worker/processors/analyze_processor.py:394)

#### DelayCut 当前实现也符合“删除型编辑映射”的思路

`script_to_delay_cuts.py` 当前是：

- 取 `{}` 内删除片段
- 在当前任务 ASR 原文中按顺序搜索
- 做短片段消歧
- 再映射到时间轴

证据：

- [script_to_delay_cuts.py](/Users/malin13/Documents/trae_projects/aicut2602/libs/cut_breakpoints/src/script_to_delay_cuts.py:219)

### 3.3 当前代码里偏离算法设计的部分

#### 偏差 A：preview API 没守住“只调删除范围”

在本轮修改前：

- `PreviewRequest.edited_script` 是 `Any`
- `start_preview()` 直接把请求体原样落库

所以系统没验证：

- 去掉 `{}` 后的正文是否仍然等于当前任务自己的 script 文本

这就是这次真正的系统层缺口。

#### 偏差 B：worker 没防御跨 task 的 edit 归属错误

在本轮修改前，`preview_processor.prepare_input()` 会读 `edit_id`，但没有校验：

- `edit.task_id == task.business_task_id`

这意味着即使真的出现跨 task edit 引用，worker 也不会马上拒绝。

#### 偏差 C：DelayCut 报错语义不对

在本轮修改前：

- `_find_time_by_content()` 找不到文本时返回 `(search_start, 0.0, 0.0)`
- `_convert_to_delay_cuts()` 再把它变成 `duration <= 0`
- 最终错误信息是“片段时长非正数”

这不符合真实问题语义。

真正问题应该是：

- “当前删除片段不在当前任务 ASR 中”

## 4.2 具体改动

### A. DelayCut 失败语义改正

在 `script_to_delay_cuts.py` 中新增了：

- `DelayCutAlignmentError`
- `AlignmentFailureDetails`

现在当删除片段在当前 ASR 中找不到时：

- 会直接抛出“未在当前 ASR 中找到删除片段”
- 不再走 `0.0, 0.0` 哨兵值
- 不再误报成“片段时长非正数”

### B. DelayCut 失败时输出结构化调试文件

`script_to_delay_cuts.py` 新增了：

- `--debug-json`

worker 容器现在会把 preview 的对齐失败现场写到：

- `preview/<edit_id>/debug_alignment_failure.json`

里面包含：

- `marked_content`
- `segment_index`
- `search_start`
- `anchor_before`
- `anchor_after`
- `asr_context`
- `script_context`
- 输入文件路径

### C. preview API 收紧输入契约

`website_aicut` 现在做了这几件事：

1. `PreviewRequest.edited_script` 改成 `str`
2. 新增 brace 格式校验
3. 新增“可见文本一致性”校验

新规则是：

- preview 允许用户改 `{}` 范围
- 但去掉 `{}` 后的可见文本必须与当前任务基线文本一致

如果不一致，API 直接返回 400，不再继续调度 worker。

### D. worker 增加 edit 归属校验

`preview_processor.prepare_input()` 现在会显式检查：

- `edit.task_id == current business_task_id`

不满足时直接 fail-fast。

### E. 容器失败 manifest 透出诊断路径

`run_stage_from_manifest.py` 现在会：

- 在 preview 调用 `script_to_delay_cuts.py` 时传 `--debug-json`
- 如果 stage 失败，先写 failed `result_manifest.json`
- 把 `debug_alignment_failure_path` 和 `failing_segment` 写进 metadata

`algorithm_runner.py` 和 `preview_processor.py` 也做了配合：

- 父进程会尽量读取容器里已经写出的 failed manifest
- preview 失败回写 manifest 时保留已有 metadata，不把 debug 路径覆盖掉

## 5. 问题点与解决方案

### 问题点 1：preview 输入边界缺失

#### 问题

系统没有验证 preview 请求是否还是“当前任务 script 的删除型编辑”。

#### 解决

在 API 边界校验：

- brace 格式合法
- 去掉 `{}` 后正文不变

### 问题点 2：跨 task edit 没有 fail-fast

#### 问题

worker 读到 edit 后，没有验证它是否属于当前 task。

#### 解决

在 `prepare_input()` 加归属校验。

### 问题点 3：定位失败的错误表达误导

#### 问题

“文本找不到”被误报为“片段时长非正数”。

#### 解决

在算法层显式抛出 alignment error，并输出 debug JSON。
