# 03 根因分析与修改建议

## 1. 根因分层

这个问题不是单一根因，而是两层问题叠在一起。

### 第一层：输入不一致

这次失败的 preview 任务 `10c7...` 使用的是：

- 当前任务自己的 `asr_result.json`
- 但编辑稿内容来自另一条任务 `c102...` 的成功 preview payload

所以它不是一组天然配套的输入。

具体证据：

- 失败任务使用的 edit：`00a468f8-9380-4af2-99c7-18ec5d39f999`
- 这个 edit 的内容来自：
  - `preview_request_real7.json`
- 而这个 JSON 来自成功任务：
  - `c10264ad-5f62-4ad9-9731-bffd0e9ce33c`

### 第二层：算法错误表达和防御不够

即使输入不一致，算法也不应该只报：

- `片段时长非正数`

更合理的是：

- 直接说明“某删除片段无法在当前 ASR 中定位”
- 并附带上下文信息，方便修复

## 2. 5 Whys

### 问题

`10c7eff8-6d4f-453b-900e-33079bad0997` 的 preview 失败。

### Why 1

为什么 preview 失败？

- `script_to_delay_cuts.py` 抛错，无法生成 `edited_delay_cuts.json`

### Why 2

为什么 `script_to_delay_cuts.py` 抛错？

- 某个删除片段被映射成了 `duration <= 0`

### Why 3

为什么会出现 `duration <= 0`？

- `_find_time_by_content()` 没在当前 ASR 文本里找到该片段，返回了 `(search_start, 0.0, 0.0)`

### Why 4

为什么找不到该片段？

- `edited_script` 中的文本与当前任务 `10c7...` 的 ASR 文本不一致

### Why 5

为什么输入会不一致？

- 重试时复用了别的任务的 `edited_script`
- 同时系统和算法都没有足够的防御来阻止或清晰报告这种情况

## 3. 我认为应该改什么

我建议把修改拆成三档。

### 档 A：必须修改

这些改动不带产品取舍，应该直接做。

#### A1. 改错误表达

在 `script_to_delay_cuts.py` 中：

- 当 `pos == -1` 且模糊搜索也失败时
- 不要返回 `(search_start, 0.0, 0.0)`
- 直接抛显式异常，比如：

```python
raise ValueError(
    f"DelayCut 定位失败：未在当前 ASR 中找到删除片段: {search_content!r}"
)
```

并带上：

- `search_start`
- `anchor_before`
- `anchor_after`
- 当前片段序号

#### A2. 给 preview 失败日志补上下文

至少在 Worker 侧的 preview 失败日志里打印：

- task_id
- edit_id
- failing marked segment
- 当前 `search_start`

这样以后不需要再人工进算法容器重放。

### 档 B：强烈建议修改

#### B1. 输入一致性保护

防止再出现“任务 A 的编辑稿喂给任务 B”的情况。

建议做法：

- 在调试脚本或 API 层明确校验：
  - `edit_id` 必须属于当前 `task_id`
- 如果允许外部直接传 `edited_script`：
  - 就要在落库前或执行前做一致性校验

这里至少要做到：

- 如果 `edited_script` 中某些片段在当前任务 ASR 里完全不存在
- 系统能快速给出清晰错误，而不是进入深层算法后才崩

#### B2. 生成更适合调试的失败产物

preview 失败时可以额外写一个失败诊断文件，例如：

- `preview/debug_alignment_failure.json`

里面包含：

- failing segment
- script context
- asr context
- anchors
- search_start

### 档 C：算法优化，可选但值得做

#### C1. 更稳的短片段/近似文本匹配

当前 `_find_time_by_content()` 主要是：

- 精确查找
- 简单去空格模糊查找
- 短片段锚点消歧

可以考虑增强：

- 统一标点归一化
- 全角半角归一化
- “的/了/呢”一类常见口语粒度容错
- 超短片段用左右锚点一起匹配，而不是只看单段文本

但注意：

- 这些优化不能建立在“跨任务输入照样要尽量跑过去”的前提上
- 先保证错误清晰，再做鲁棒匹配

## 4. 我认为什么样的修改是合适的

最合适的修改标准是：

1. **先把错误说明白**
- 输入不一致时，要明确报“找不到删除片段”

2. **再把失败留得住**
- 失败后要有可直接复盘的结构化产物

3. **最后再提升匹配鲁棒性**
- 能容忍轻微 ASR 差异
- 但不能掩盖严重输入错配

如果只让我选一件必须先做的事，我会选：

- **A1：把“找不到文本”从 `duration <= 0` 里分离出来，变成明确异常**

因为这一步成本最低，收益最高，且不改变算法行为。

## 5. 不建议怎么改

这些方向我不建议：

1. 不要简单地在 `duration <= 0` 时跳过该片段继续跑
- 会导致输出 silently wrong

2. 不要为了“让它能过”就把找不到的片段默认映射到某个近邻时间
- 这会污染剪辑结果

3. 不要把跨任务复用编辑稿当正常操作来兼容
- 系统层应该阻止这种错误输入

## 6. 修改后的验收标准

新的 coding agent 改完后，至少要满足：

### 最低标准

1. 对当前 `10c7...` 这次失败，报错要从：
- `片段时长非正数`

变成更明确的：
- `未在当前 ASR 中找到删除片段`

2. 错误信息里要能看出是哪段文本失败

### 更高标准

1. 对轻微文本差异可以自动定位成功
2. 对严重不一致仍然 fail-fast
3. 失败时能输出结构化诊断文件
