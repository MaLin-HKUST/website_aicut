## 3. 修改完成后，应该怎样把结果交回

我建议对方按下面格式交回：

### 交付物 1：代码提交

必须提供：

- 仓库路径
- 分支名
- commit SHA

如果是在 `aicut2602` 仓改：

- 给我 `branch + commit SHA`

如果还需要联动 `website_aicut`：

- 两边都给我各自的 `branch + commit SHA`

### 交付物 2：改动说明

至少写清：

1. 改了哪个文件
2. 改了哪几个函数
3. 是只改报错，还是连匹配策略一起改了
4. 是否新增了调试产物或日志

### 交付物 3：复现前后对比

必须包含：

1. 失败样本修改前的报错
2. 失败样本修改后的结果
3. 成功样本修改后的结果

建议格式：

```markdown
Before:
- failing case: ...
- error: ...

After:
- failing case: ...
- result: ...
- whether output file generated: ...

Regression:
- successful case: ...
- still passes: yes/no
```

### 交付物 4：运行证据

至少给我：

- 失败样本命令行输出
- 成功样本命令行输出
- 如果生成了 `edited_delay_cuts.json`，给出文件路径

我拿到对方的修改后，会做这几件事：

1. 审代码
2. 用当前 `website_aicut` 的真实链路重新验证
3. 判断是否把该修改并入当前正式运行面
4. 再继续推进 `10c7...` / `a334...` 这些真实任务

所以对方给我的结果，最好是：

- 能直接 checkout
- 能直接运行
- 能直接对照当前问题复现和验证

## 5. 建议对方使用的提交规范

如果对方要提交 git，建议至少包含这些信息：

- 为什么改
- 修改的是“错误表达”还是“匹配逻辑”
- 改动风险
- 验证了哪些样本

## 6. 对另一个 coding agent 的直接指令

1. 先复现当前失败
2. 先把“找不到文本”的错误表达改清楚
3. 再决定要不要增强匹配策略

5. 修改后必须同时验证：
   - 当前失败样本
   - 已有成功样本
