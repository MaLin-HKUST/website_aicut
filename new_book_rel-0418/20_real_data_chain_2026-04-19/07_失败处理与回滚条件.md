# 07_失败处理与回滚条件

本文回答什么问题：

- 真实数据联调过程中出现问题时应该怎么分流处理
- 哪些失败可以直接重试
- 哪些失败必须停下来修代码或回滚

## 原则

1. 优先保留证据
2. 不要因为一次失败就覆盖旧 artifacts
3. 不要为了继续推进而跳过失败原因

## 失败分类

### A 类：可重试失败

特点：

- 不涉及代码变更
- 不涉及运行面损坏
- 原因明显是暂时性或时序性问题

包括：

- 网络抖动
- TOS 单次上传失败
- 任务轮询超时但后台还在跑
- preview / finalize 因时序问题需要重试

处理方式：

- 保留本次失败 artifacts
- 新建下一次运行目录
- 明确记录“重试原因”

### B 类：需要停下修代码的问题

包括：

- `upload-direct` 固定失败
- analyze 无法落 TOS 产物
- Worker 无法消费任务
- `apps/services/tos_service.py` 再次出现真实 TOS 访问错误
- 任务详情接口返回不一致状态

处理方式：

- 停止继续联调
- 先修代码或修发布真相
- 修完后重新从 Step 0 或 Step 3 开始

### C 类：需要回滚运行面的失败

包括：

- 正式域名入口异常
- nginx upstream 被错误改坏
- legacy API / SQLite 受影响
- 当前正式运行面崩溃

处理方式：

- 立即按 `10_rebuild_2026-04-18/08_验收与回滚手册.md` 回滚
- 不在本专项内继续盲调

## 常见失败点的处理规则

### 1. `upload-direct` 失败

处理顺序：

1. 保留失败响应
2. 检查 nginx / API / 文件大小 / TOS 中转路径
3. 允许改走：
   - `upload-prepare`
   - 直传 TOS
   - `upload-complete`

注意：

- 只要 fallback 路径成功，本轮链路仍可继续
- 但必须在报告里写明主路径失败事实

### 2. analyze 卡死或失败

处理顺序：

1. 保留 analyze 任务 ID
2. 拉 Worker 日志
3. 拉 TOS 对象清单
4. 检查调度任务状态

如果是 TOS 输入不存在、Worker 失联、或调度任务未被消费，则不继续 preview。

### 3. preview 失败

处理顺序：

1. 保留 `active_edit_id`
2. 检查 preview 输入是否完整
3. 检查 Worker preview 日志
4. 检查 preview 音频对象是否部分生成

### 4. finalize 失败

处理顺序：

1. 先区分：
   - 真失败
   - 仅环境降级
2. 如果是 `ffprobe` 缺失但最终视频仍生成：
   - 记为 `degraded pass`
3. 如果最终视频未生成：
   - 记为失败，进入代码/环境修复

### 5. Worker 失联

处理顺序：

1. 检查 gateway 健康状态
2. 检查 tunnel 是否还在
3. 检查 A 机器 PostgreSQL 与 API 是否可达
4. 若 Worker 不可恢复，不继续执行真实数据任务

## 回滚门槛

以下情况必须优先考虑回滚，而不是继续调试：

- 正式域名页面不可访问
- 正式登录链路受损
- legacy API / SQLite 受损
- nginx 被切到错误运行面

## 对 Agent 的直接指令

- 如果问题只影响真实数据任务本身，优先保留证据并停在任务层面。
- 如果问题已经影响正式运行面，优先回滚，不要继续推进本专项。
