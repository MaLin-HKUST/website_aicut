# 20_real_data_chain_2026-04-19

本文回答什么问题：

- 当前系统已经恢复到可运行状态之后，接下来如何用真实数据跑通 Smart Cut 全链路
- 真实数据放在哪里
- 当前正式链路还缺什么
- 后续 Agent 应该按什么顺序推进真实数据联调、证据落档和发布收口

## 本层定位

这一层不是长期架构规则，也不是 2026-04-18 那轮“把系统从混乱状态拉回可运行状态”的重建战役本身。

这一层专门回答：

- 如何在**当前正式运行面**上用**真实数据**验证 Smart Cut
- 如何把“已经能跑但带热补”的线上状态继续收口成更稳定的标准发布状态

可以把它理解为：

- `10_rebuild_2026-04-18/` 负责“先把系统救活并收口”
- `20_real_data_chain_2026-04-19/` 负责“在当前正式运行面上用真实数据把业务链真正跑通，并为后续标准化发布做准备”

## 当前结论

截至 2026-04-19：

- 系统已经具备可用的正式入口和可用的 Worker 执行链
- phase 7 已证明当前链路可以跑到 `success`
- 但 phase 7 使用的是临时生成的测试视频字节，不是本层要求的真实样本
- 当前线上仍存在热补：
  - `apps/services/tos_service.py`
  - `apps/api/routes/tasks.py`
- Worker finalize 环境仍缺 `ffprobe`
- `/smart-cut` 当前交互生命周期仍与目标产品语义不一致，已拆入 `50_smart_cut_workspace_refactor_2026-04-21/`

因此，本层的目标不是再做一次抽象验证，而是：

- 用真实样本在正式链路上重跑闭环
- 留下完整证据
- 再把当前“热补可用态”推进到“标准发布可重复态”
