# Smart Cut 并行开发总协调

本文回答什么问题：

- 并行开发应该怎么排期
- 哪些任务可并行，哪些任务必须等待前置完成
- 每个 agent 应该在什么时机开始工作
- 主集成人如何接收和整合这些交付

## 总原则

- 本轮不是自由发挥，而是严格按 [../task.json](../task.json) 的 `R00-R11` 推进。
- 契约层先行，页面和交互层后行。
- 并行只发生在写入范围明确且不会相互踩文件的情况下。
- 每个 agent 都必须遵守仓库根 `AGENTS.md` 和本专项文档，不得自行改产品决策。

## 并行时间线

### Phase A：契约锁定

先启动：

- Agent 01

原因：

- `R01-R02` 决定 `visible_in_task_center`、`session_scope_id`、`current draft`/`ensure draft` 这些接口和数据语义
- 这些不锁定，其他 agent 改页面或任务中心都会返工

启动门槛：

- 现在就可以开始

完成标志：

- 有独立 branch
- 有 Lore commit
- 有接口/字段/事务边界说明
- 主集成人已审阅并接受契约

### Phase B：并行编码第一批

在 Agent 01 的契约被接受后，同时启动：

- Agent 02
- Agent 03

原因：

- Agent 02 改 `task-center` 可见性
- Agent 03 改 `/smart-cut` 入口和 analyze 回显
- 两者依赖同一组契约，但写入范围可以做到基本分离

启动门槛：

- Agent 01 回交完成，主集成人认可

### Phase C：并行编码第二批

在 Agent 03 的页面骨架稳定后，再启动：

- Agent 04

原因：

- `preview` 与 `finalize` 直接建立在草稿工作台已可恢复、analyze 已可回显的前提上
- 如果 Agent 04 太早开始，会持续猜测上游页面状态和接口形状

启动门槛：

- Agent 03 至少完成 `R04-R06` 的主路径设计与初版实现

### Phase D：集成验证

在 Agent 02、03、04 基本整合后，再启动：

- Agent 05

原因：

- Agent 05 不是提前造方案，而是拿当前集成后的实现跑真实浏览器、回写文档与证据

启动门槛：

- `R03-R09` 至少有一版可运行实现

## 主集成人的集成顺序

固定顺序：

1. 接收 Agent 01，锁定契约
2. 接收 Agent 02，锁定任务中心语义
3. 接收 Agent 03，锁定入口与 analyze 页面态
4. 接收 Agent 04，锁定 preview/finalize/workspace reset
5. 接收 Agent 05，锁定真实浏览器回归和文档结论

不得反过来：

- 不要先合 Agent 04 再补 Agent 03
- 不要在 Agent 05 的真实回归还没开始时就声称专项完成

## 交付门槛

每个 agent 回交时必须同时给：

- `branch`
- `commit SHA`
- `改动文件列表`
- `实际运行过的验证命令`
- `剩余风险`
- `与 task.json 的对应关系`

缺失任一项：

- 不接手
- 不合并
- 不上线

## 对主集成人的直接指令

- 如果不同 agent 交回的契约冲突，以 Agent 01 的已接受结论为准。
- 如果 Agent 03 和 Agent 04 修改同一前端文件，必须先在主集成人这里重排 write scope，再允许编码。
- 所有 agent 的工作都要回写到 [../progress.md](../progress.md) 与 [../progress.json](../progress.json)，由主集成人统一维护。
