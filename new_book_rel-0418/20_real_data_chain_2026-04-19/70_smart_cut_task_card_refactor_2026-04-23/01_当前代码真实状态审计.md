# 当前代码真实状态审计

## 结论

当前仓库里的 Smart Cut 仍然是 **隐藏草稿模型**，不是即将重构的“显式主任务卡模型”。

这一步的目的不是评价对错，而是把“当前真实代码是什么”写死，避免后续设计建立在口头假设上。

## 后端真实状态

### 1. `smart_cut_tasks` 仍然是隐藏草稿主表

文件：
- `apps/models/task.py`

当前真实字段和语义：
- `user_id`
- `status`
- `current_stage`
- `task_title`
- `visible_in_task_center`
- `session_scope_id`
- `original_video_url`
- `reference_text_url`
- `analyze_script`
- `asr_result_tos_key`
- `active_edit_id`
- `final_video_url`

关键事实：
- `visible_in_task_center=false` 仍然代表隐藏草稿
- `visible_in_task_center=true` 才进入任务中心
- `session_scope_id` 仍然存在，并被用于当前草稿查找
- 主模型里 **没有 `company_id`**

### 2. 当前状态机仍然围绕隐藏草稿推进

文件：
- `apps/models/task.py`

当前状态枚举：
- `waiting_upload`
- `ready_analyze`
- `analyzing`
- `analyze_failed`
- `waiting_user`
- `previewing`
- `preview_failed`
- `finalizing`
- `finalize_failed`
- `success`
- `abandoned`

关键事实：
- `preview_failed` 仍然是主任务状态，而不是子执行失败记录
- `waiting_user` 同时承载 analyze 后和 preview 后的“用户回合”
- 终态定义里把 `analyze_failed / preview_failed / finalize_failed` 也视为终态

### 3. 当前仍存在 draft/current 系列接口

文件：
- `apps/api/routes/tasks.py`

当前真实接口和辅助逻辑：
- `GET /api/smart-cut/tasks/draft/current`
- `POST /api/smart-cut/tasks/draft/current/ensure`
- `_find_current_hidden_draft(...)`

关键事实：
- 当前主入口仍然依赖“找当前隐藏草稿”
- 草稿恢复和主任务存在性不是显式任务卡模型

### 4. 当前任务中心普通用户视图仍按 `user_id` 过滤

文件：
- `apps/api/routes/task_center.py`

当前真实逻辑：
- `/api/task-center/tasks` 默认从 `SmartCutTask.visible_in_task_center=true` 查
- 传 `user_id` 时按 `SmartCutTask.user_id == user_id` 过滤

关键事实：
- 当前任务中心不是公司级可见性模型
- 普通用户列表仍以 `user_id` 为主

### 5. 当前没有 `smart_cut_task_runs` 子执行表

当前仓库事实：
- 没有主任务 + 子执行记录这层模型
- analyze / preview / finalize 的执行信息主要散落在：
  - `scheduler_tasks`
  - `smart_cut_edits`
  - `smart_cut_tasks.status/current_stage`

这就是当前“页面状态和调度状态容易分裂”的根源之一。

## 前端真实状态

### 1. Smart Cut 活跃影响面不只在 `app/smart-cut`

当前仍会影响 Smart Cut 的活跃文件包括：
- `apps/web/components/navigation/use-user-workspace-data.ts`
- `apps/web/lib/task-center.ts`
- `apps/web/components/task-center/task-center-shell.tsx`
- `apps/web/components/navigation/user-workspace-shell.tsx`

关键事实：
- 即使 `/smart-cut` 入口已经下线，这些文件依然承接 Smart Cut 的任务中心、侧边栏 preview 和 workspace 指标逻辑
- 后续重构不能只看 `apps/web/app/smart-cut/*`

### 2. 当前 live 已下线的是“旧入口”，不是后端 API

当前已完成：
- `/smart-cut` 和 `/smart-cut/[taskId]` 已切到维护页
- 旧前端 Smart Cut 实现已移到 quarantine

当前未完成：
- Smart Cut 后端 API 还存在
- scheduler / worker 路径仍保留旧模型语义

## 文档真实状态

### 1. `50_*` 仍描述旧隐藏草稿模型

历史包：
- `new_book_rel-0418/20_real_data_chain_2026-04-19/50_smart_cut_workspace_refactor_2026-04-21/`

它的价值：
- 记录旧重构思路和分段上线过程

它的限制：
- 不再适合作为继续实现的主依据
- 因为新的重构目标已经改成显式任务卡模型

### 2. `70_*` 当前必须承担唯一执行主包职责

所以后续所有实现都必须先看：
- 当前代码到底是什么
- 和目标模型差距在哪里

不能再默认“某个之前的口头结论已经落到代码里了”。

## 差距汇总

当前代码 vs 目标模型的关键差距：

1. 当前是隐藏草稿模型，目标是显式主任务卡模型
2. 当前按 `user_id` 过滤任务中心，目标是公司级共享主任务可见性
3. 当前没有 `task_runs`，目标是主任务下的子执行 timeline
4. 当前 `preview_failed` 是主任务状态，目标是 preview 失败只记在 run 级别
5. 当前 finalize 默认依赖 preview，目标是 analyze-only 也能直接 finalize
6. 当前依赖 `draft/current`，目标是显式 `开启任务 / 继续处理 / 放弃任务`

## 约束

后续设计必须基于以下事实展开：

- 不要在旧模型上继续补 `draft/current`
- 不要再把“隐藏草稿恢复”当成核心产品能力
- 不要假设 `company_id` 已经在 Smart Cut 后端落地
- 不要假设已有子执行表
