# Smart Cut 状态机仿真矩阵

## 目的

这个矩阵不运行浏览器、真实 worker、docker 或算法，只构造 PostgreSQL 表状态，然后调用本地 scheduler/task-center 逻辑，验证用户重新打开页面时看到的反馈是否和调度系统结论一致。

## 单一真相规则

- 用户可见主状态来自 `smart_cut_tasks`。
- 底层执行真相来自 `scheduler_tasks` 和 `smart_cut_task_runs`。
- worker 容器状态只通过 `smart_cut_devices` 表表达。
- 页面展示优先使用 task-center 归一化结果，不允许前端自己把多个业务任务覆盖成多个 `running`。

## 正向路径

| 场景 | 初始业务状态 | scheduler 状态 | device 状态 | scheduler 应得结论 | 用户重新打开页面应看到 |
| --- | --- | --- | --- | --- | --- |
| 创建后未上传 | `waiting_upload/upload` | 无 | 无 | 等待用户上传 | 工作台显示待上传素材，任务列表显示排队中 |
| 上传完成待分配 | `ready_analyze/analyze` | `pending/analyze` | idle 空闲 | 分配给可用 worker | 任务列表显示排队中 |
| analyze 已分配未领取 | `analyzing/analyze` | `assigned/analyze` | `idle + current_task_id=analyze` | 等 worker 领取 | 任务列表显示执行中或排队中，但只允许一条执行中 |
| analyze 运行中 | `analyzing/analyze` | `running/analyze` | `running + current_task_id=analyze` | 等 worker 输出 | 显示正在分析 |
| analyze 完成一键直通 | `analyzing/analyze` | `post/result` 或 `running/result` | `post` 或遗留 `idle+current_task_id` | 标记 analyze run 成功，排 finalize | 显示正在生成视频，不显示待人工确认 |
| finalize 已分配 | `finalizing/finalize` | `assigned/finalize` | `idle + current_task_id=finalize` | 等 worker 领取 | 显示正在生成视频或排队中，不能显示人工确认 |
| finalize 运行中 | `finalizing/finalize` | `running/finalize` | `running + current_task_id=finalize` | 等视频/字幕输出 | 显示正在生成视频或正在生成字幕 |
| finalize 完成 | `finalizing/finalize` | `post/result` | `post/current_task_id=finalize` | 写 final_video_url/subtitle_srt_url 并成功 | 显示已完成，可下载视频和字幕 |

## 页面操作路径

| 用户操作 | 后台允许状态 | 期望状态推进 | 重新打开页面 |
| --- | --- | --- | --- |
| 上传素材但不点一键生成 | `waiting_upload` -> `ready_analyze`，普通流程可进入 analyze | 普通流程 analyze 后可进入 `waiting_user` | 显示待人工确认/试听 |
| 上传后点击一键生成 | payload 带 `auto_finalize_after_analyze=true` | analyze 成功后自动排 finalize | 显示正在生成视频/字幕，不出现继续处理停顿 |
| 用户关闭浏览器 | 任意非终态 | 不影响 scheduler 和 worker | 按 task-center 当前归一化状态恢复 |
| 用户放弃任务 | 非终态且业务允许 abandon | 业务任务 `abandoned`，run 可标记 abandoned | 任务列表显示失败/已放弃，不能继续自动调度 |
| 失败后重新打开 | `*_failed` | 不自动重试 | 展示失败原因，用户需要放弃或重新开任务 |

## 错误与异常组合

| 异常组合 | 以前风险 | 现在预期 |
| --- | --- | --- |
| `scheduler=running + result!=null + device=idle/current_task_id` | analyze 已完成但业务卡死在正在分析 | scheduler 自愈闭环，排 finalize，清掉旧 worker 指针 |
| `scheduler=post + result!=null + device 行不存在` | 依赖 device POST 导致无法闭环 | scheduler 仅凭 scheduler result 也能闭环 |
| `device=idle/current_task_id + scheduler=assigned` | 这是合法“已分配待领取” | 保留，等待 worker poll |
| `device=idle/current_task_id + scheduler=success/failed/timeout` | worker 被占住，后续任务无法分配 | 释放 worker current_task_id |
| analyze 闭环被重复执行 | 可能重复创建 finalize | `_queue_finalize_after_analyze` 幂等复用已有活跃 finalize |
| worker 成功但 scheduler 未看到 device POST | 容易停在 running | worker 成功时先写 `scheduler_tasks.status=post` 和 `result` |

## 仍需人工验收

- 线上部署后观察真实任务是否从 analyze 自动进入 finalize。
- TOS 大文件上传 timeout 仍需要独立处理，它不是状态机闭环问题。
- 前端一键按钮的禁用交互和普通上传/一键上传分支需要单独 UI 验收；本矩阵只证明 scheduler 状态结论。
