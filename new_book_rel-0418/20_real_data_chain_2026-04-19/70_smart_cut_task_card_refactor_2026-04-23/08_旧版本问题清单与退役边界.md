# 旧版本问题清单与退役边界

## 目的

把旧 Smart Cut 模型中已经确认的问题集中列清，避免它们继续以“历史遗留兼容”名义混回新方案。

## 已确认的旧版本问题

### 1. 隐藏草稿与真实调度双真相

表现：
- 页面显示有一条当前草稿
- scheduler / worker 却不认识这条任务

结论：
- 隐藏草稿不能继续作为主模型

**状态：已修复**（2026-04-24）
**修复方式**：新模型以 `smart_cut_tasks` 为主任务真相，`smart_cut_task_runs` 为执行真相，scheduler 只承担底层派单。

### 2. `draft/current*` 让页面恢复逻辑承担主真相职责

表现：
- 页面靠 `draft/current`
- 任务存在性和页面恢复混在一起

结论：
- `draft/current`
- `draft/current/ensure`
- `draft/current/abandon-all`
  都必须退役

**状态：已修复（功能层面），代码待清理**（2026-04-24）
**修复方式**：新 `POST /api/smart-cut/tasks/start` 替代草稿自动创建，前端不再调用 draft 接口。

### 3. `session_scope_id` 被错误用作主归属条件

表现：
- 刷新/换会话后，任务在，但页面认不回来

结论：
- `session_scope_id` 可保留审计意义
- 不能继续承担主任务恢复语义

### 4. `visible_in_task_center` 控制任务是否存在

表现：
- 同一业务任务在“隐藏草稿”和“正式任务”之间切换

结论：
- 主任务应从创建开始就可见
- `visible_in_task_center` 作为核心语义字段必须退役

### 5. 任务中心按 `user_id` 过滤

表现：
- 当前普通用户只按 `user_id` 看任务
- 无法承接公司级任务卡模型

结论：
- 新模型必须迁移到 `company_id` 视角

**状态：已修复**（2026-04-24）
**修复方式**：任务中心普通用户列表优先按 `company_id` 过滤，回退到 `user_id`。

### 6. 子执行失败直接污染主任务状态

表现：
- `preview_failed`
- `analyze_failed`
- `finalize_failed`
  现在都在主任务状态机里

结论：
- 子执行失败应下沉到 run 层
- 主任务应尽量回到可继续处理态

**状态：已修复**（2026-04-24）
**修复方式**：preview/finalize 失败不再把主任务标记为失败态，主任务回到 `waiting_user`，失败信息记录在 `task_runs.error_message`。

### 7. finalize 强依赖 preview

表现：
- 用户觉得 analyze 结果已经够好，也不能直接生成视频

结论：
- 必须支持 analyze-only finalize

**状态：已修复**（2026-04-24）
**修复方式**：finalize 允许无 preview 产物时直接基于 analyze 结果生成，空 `pause_cuts` 传结构化对象而非列表。

### 8. 旧分支历史污染新专项

表现：
- `70_*` 初始进度记录仍挂着：
  - `feature/smart-cut-workspace-refactor-R10-R11-integration`

结论：
- 新专项统一切到：
  - `feature/smart-cut-taskcard-refactor`
- 旧分支只保留为 `L00` 历史来源

## 退役边界

### 必须退役

- 隐藏草稿主模型
- `draft/current*`
- `session_scope_id` 主归属逻辑
- `visible_in_task_center` 主控制逻辑
- finalize 必须先 preview 的硬限制

### 只作为历史事实保留

- `50_*` 专项包
- `fcb3e11` 及其旧分支来源
- 旧前端 quarantine 包
- 上线前备份记录

### 当前不退役

- `L00` 备份与下线文档
- 已完成任务下载能力
- 维护页 runtime

## 执行原则

- 新代码只围绕显式主任务卡模型设计
- 不再给旧隐藏草稿语义补兼容层
- 如果文档引用旧逻辑，必须标注为“历史来源”，不能写成现行依据
