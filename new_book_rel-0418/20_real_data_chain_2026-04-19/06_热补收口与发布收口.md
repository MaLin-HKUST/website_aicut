# 06_热补收口与发布收口

本文回答什么问题：

- 真实数据链路跑通之后，下一步为什么不是“结束”
- 当前线上热补要如何收口
- 发布真相要如何重新统一

## 当前已知热补

截至 2026-04-19，当前线上 candidate 链路已知热补包括：

- `apps/services/tos_service.py`
- `apps/api/routes/tasks.py`

这些热补让当前线上功能可用，但仍存在问题：

- 线上容器内实际代码与标准构建产物不完全一致
- 后续 Agent 容易误判“git HEAD 就是线上真相”

## 当前发布真相还没有完全收口

当前线上应该理解为三层真相同时存在：

1. git 提交真相
2. release manifest 真相
3. 容器内热补真相

这不是长期可接受状态。

## 真实数据链路跑通后的下一步

真实数据闭环跑通后，下一步固定是：

1. 把热补代码合并回标准构建输入
2. 用标准构建重新生成 candidate / 正式运行面
3. 用同一真实样本再次回归
4. 只有回归通过，才可以把“热补状态”从 `11` / `12` 文档中移除

## Worker 环境收口

当前 Worker 已知缺口：

- finalize 缺 `ffprobe`

因此，Worker 环境收口至少应包含：

1. 明确 Worker 镜像或宿主机环境里如何提供 `ffprobe`
2. 补齐后用同一真实样本再次跑 finalize
3. 对比补齐前后结果差异

## 发布收口目标

最终目标是把当前线上恢复成：

- git commit 真相
- 标准构建真相
- 标准发布脚本真相
- 文档真相

四者一致。

## 本文件不做什么

本文只定义“为什么要收口、收口方向是什么”，不直接给出详细代码修改步骤。

详细执行应放入后续专项或执行计划中，而不是和本专项真实数据验证混在一起。

## 对 Agent 的直接指令

- 真实数据联调通过后，不要直接宣布系统“完全完成”。
- 先看热补有没有收口进标准构建。
- 如果没有，就继续推进发布收口，而不是把当前热补状态长期固化。
