# 调试与部署过程记录

这轮关键问题与收口方式如下。

## 1. 部署真相不唯一

最初的问题不是单个功能逻辑，而是前端运行面、API 运行面、PostgreSQL schema、TOS 上传路径长期不同步。

收口动作：

- 禁止继续用 `next dev`
- 前端改成 production runtime
- Smart Cut API 独立跑在 `18002`
- 真实浏览器直接打正式站

## 2. Upload 真实链路

先后验证过两条路径：

- `upload-direct`：浏览器 -> A 机 -> TOS
- `upload-prepare -> 浏览器直传 TOS -> upload-complete`

最终主路径固定为第二条，因为：

- 体验更接近旧系统里“上传感觉是正常的”
- 不再让 A 机 relay 大文件到 TOS

关键提交：

- `974ad23` 稳定 TOS SDK timeout / retry
- `6cd749e` 暴露 multipart 上传进度
- `01f79ee` 改成浏览器直传 TOS 为主路径

## 3. Analyze 真执行

Upload 跑通后，Analyze 真正入了调度并落到 `worker1-phase6`。

中间暴露过一次调度器状态问题：

- `sqlalchemy.exc.PendingRollbackError`

当时的现场处理是：

- 重启 `a-machine-phase5-scheduler`

结论：

- Analyze 主链是通的
- 调度器异常回滚能力后续还要补代码
