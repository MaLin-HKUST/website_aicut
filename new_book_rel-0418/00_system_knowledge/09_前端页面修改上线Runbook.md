# 09. 前端页面修改上线 Runbook

本文回答什么问题：

- 前端页面改完以后，主集成人应该按什么顺序验证、截图、上线
- 哪些步骤是必做，哪些证据必须保留
- 如何避免再次出现“只看代码、没看真实线上效果”的低效流程

本文是执行细则。
前端发布原则与唯一默认路径，以 [11_前端发布单一路径.md](./11_前端发布单一路径.md) 为准。

## 1. 适用场景

这份 runbook 适用于：

- 用户端页面视觉调整
- Smart Cut、TTS、任务列表、登录页等前端改版
- 已经拿到前端 agent 的代码交付，需要集成、上线、截图验收

不适用于：

- 调度中心重建
- Worker 算法修复
- 数据库迁移

## 2. 当前默认策略：按单一路径执行

当目标是：

- 快速看到页面效果
- 快速确认用户是否满意
- 快速推进到“页面可点、可看、可继续迭代”

默认采用 `11_前端发布单一路径.md` 里的：

- `3302` 预览口
- 用户确认
- 生产工件 promotion 到 `3301`

这套策略下的硬规则：

- 本节不再单独定义另一套原则，避免与 `11` 冲突

当前阶段的优先级是：

- 先确认页面是否对、是否能用
- 用户确认视觉和交互都对以后，再决定是否进入更重的发布收口流程

## 3. 线上优先原则

当前项目的前端页面迭代，默认只对照线上结果。

原因：

- 本地环境与线上环境不一致
- 本地保存大体积镜像和构建产物成本高
- 当前任务目标是尽快看到真实页面效果，而不是先证明离线流程完美

因此：

- 页面改动是否正确，以正式站截图和正式站 Playwright 观测为准
- 本地验证只保留最小必要项，例如类型检查、目标页面局部测试
- 不再默认做“本地镜像构建 -> 本地镜像验收 -> 线上替换”这一整套

## 4. 前置输入

执行前，主集成人必须已经拿到这些输入：

1. 前端 agent 的交付信息
- `branch`
- `commit SHA`
- `改动文件列表`
- `实际运行过的验证命令`

2. 页面设计输入
- 当前截图
- 目标截图
- 用户明确指出的不满意点

3. 环境信息
- 当前正式站域名
- 当前正式前端运行面
- 可登录的验收账号
- 当前线上任务 ID（如果页面依赖真实任务）

缺少以上任一关键输入时，不应直接进入上线阶段。

## 5. Step-by-step 执行流程

### Step 1：检查交付是否完整

要做什么：

- 核对前端 agent 是否给全 4 个核心字段
- 核对改动文件是否确实属于前端任务范围
- 核对有没有越界修改接口、数据库、调度、Worker

完成标准：

- `branch / commit SHA / 改动文件列表 / 验证命令` 4 项齐全
- 改动范围与页面任务一致

检查方法：

- `git show <commit>`
- 对照任务书和改动文件列表

如果失败：

- 不进入集成
- 直接要求前端 agent 按模板补全

### Step 2：在本地集成代码

要做什么：

- 如果对方给的是可用 commit，优先 `cherry-pick`
- 如果对方只交工作树结果，先手工审 diff，再最小范围集成

完成标准：

- 目标改动已经进入主集成人当前工作分支
- 没混入无关脏文件

检查方法：

- `git diff --name-only`
- 只应出现本次页面改动相关文件

### Step 3：先做最小验证

要做什么：

- 跑前端最小必要验证，只覆盖当前页面能否安全进入线上：
  - `tsc --noEmit`
  - 对应页面相关 Playwright/单测
  - 仅当当前线上替换路径确实依赖生产构建时，才补 `npm run build`

完成标准：

- 目标页面相关验证通过
- 如存在已知旧失败，要明确记录“与本次改动是否相关”

检查方法：

- 保存命令和输出摘要
- 明确 pass/fail

### Step 4：发布到预览口

要做什么：

- 把目标前端版本发到 A 机预览口 `3302`
- 不直接替换正式口 `3301`
- 优先用最短路径让用户先看到预览效果

完成标准：

- `3302` 已经起来
- 预览版本已经可访问

检查方法：

- 核对当前运行进程和端口
- 截图或局部页面探测

### Step 5：预览口浏览器登录验收

要做什么：

- 用真实账号登录预览口
- 至少验证：
  - `/login`
  - 登录后默认页
  - 被修改页面
  - 如页面依赖真实任务，打开目标任务页

完成标准：

- 登录成功
- 页面真实呈现符合本轮改动目标

检查方法：

- 浏览器截图
- 如有需要，保存：
  - 登录前截图
  - 登录后截图
  - 改动页截图

### Step 6：用户确认后再替换正式口

要做什么：

- 只在用户确认预览正确以后，才把工件 promotion 到 `3301`

完成标准：

- `3301` 切换到确认过的版本
- 正式口不运行 `next dev`

检查方法：

- 核对当前 `3301` 运行方式
- 核对正式站命中的页面标记

### Step 7：补一条正式站 Playwright 验收

要做什么：

- 至少新增或复用一条正式站 UI 验收
- 优先做“观测型验收”，不要让浏览器负责跑长时间真实任务

完成标准：

- Playwright 在正式站上通过
- 证明页面可登录、可进入、可见关键 UI 元素

检查方法：

- 保存执行命令
- 保存通过结果

### Step 8：把“上线事实”写回 codebook

要做什么：

- 把这次前端上线的关键事实写回文档
- 至少记录：
  - 改动 commit
  - 上线时间
  - 验证账号
  - 真实截图位置
  - Playwright 命令
  - 已知剩余风险

完成标准：

- 下一个 agent 不需要翻聊天记录，就能知道这次前端是怎么上线和验收的

检查方法：

- 文档里能独立回答：
  - 改了什么
  - 怎么验的
  - 线上看到什么

## 6. 本轮经验总结成的硬规则

### 4.1 不要只用 `curl` 判断前端是否生效

`curl` 只能证明文本存在，不能证明布局、比例、配色、模块位置正确。

### 4.2 必须做“真实登录 + 真实页面截图”

只跑 API 或只看源码，不足以说明页面真的符合预期。

### 4.3 Playwright 更适合做“线上观测验收”

对于长时间真实任务页面：

- 不要让 Playwright 浏览器负责上传大文件和跑完整链路
- 先有真实任务，再让 Playwright 去看任务页面和下载入口

### 4.4 前端上线必须留图片证据

至少保留：

- 登录前截图
- 登录后截图
- 目标页面截图

### 4.5 前端 agent 的交付质量不好时，不要硬等

如果对方没给可 cherry-pick 的 commit，但改动范围已明确：

- 可以由主集成人审查工作树后手工收口
- 但必须把这次偏离模板的事实写明

### 4.6 当前默认不做本地镜像/本地镜像对照

除非未来有独立测试服，否则当前前端页面改版不应默认做：

- 本地镜像构建
- 本地镜像验收
- 本地镜像与线上镜像差异分析

当前默认做法是：

- 预览口
- 预览截图
- 用户确认
- 正式口 promotion
- 正式站 Playwright 观测

## 7. 推荐的最小命令集

以下不是固定唯一命令，但应覆盖这些能力：

```bash
# 1. 看交付是否完整
git show <commit>

# 2. 做静态验证
cd apps/web && npx tsc --noEmit
cd apps/web && npx playwright test tests/<target>.spec.ts --reporter=line

# 3. 本地 build（必要时）
cd apps/web && npm run build

# 4. 正式站 UI 观测
PLAYWRIGHT_BASE_URL=https://xiaomajianji.cn \
PLAYWRIGHT_USERNAME=<user> \
PLAYWRIGHT_PASSWORD=<password> \
npx playwright test tests/<live-spec>.spec.ts --config playwright.config.ts --reporter=line
```

## 8. 本地与线上都应该保留什么证据

至少保留：

- 本次集成 commit
- 实际执行过的验证命令
- 正式站截图
- Playwright 结果
- 上线后命中的页面标记

不必默认纳入 git 的内容：

- 敏感 cookie
- 临时 token
- 带预签名 URL 的原始抓包

## 9. 对 Agent 的直接指令

- 如果你是主集成人，前端上线验收至少要做到：代码验证、真实登录、真实截图、正式站 Playwright 观测。
- 如果你没有看到真实截图，就不要向用户宣称“页面已经对了”。
- 如果你只做了 `curl` 或源码检查，结论必须表述为“文本命中”，不能表述为“页面视觉已确认”。
- 当前阶段默认不做本地镜像对照；如果你想引入更重的流程，先确认用户要的不是“快速看效果”，而是“正式收口发布”。
