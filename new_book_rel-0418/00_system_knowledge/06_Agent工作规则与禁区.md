# 06. Agent 工作规则与禁区

本文回答什么问题：

- 新 Agent 进入项目后必须先做什么
- 哪些架构错误是历史上已经发生过、禁止再犯的
- 哪些情况下必须先更新文档再动代码

## 1. 进入项目后的默认动作

普通功能开发 Agent 必须：

1. 先读 `README.md`
2. 再读 `00_system_knowledge/01_系统定义.md`
3. 再读 `00_system_knowledge/02_系统架构与职责边界.md`
4. 再读本文件

只有在做重建、发布、备份、运维时，才需要进入 `10_rebuild_2026-04-18/`。

## 2. 绝对禁区

### 2.1 禁止把 Worker 侧逻辑长期部署在 A 机器

禁止对象：

- Worker Gateway
- Smart Cut Worker

如果只是临时单步验证，也必须明确说明是临时验证，而不是正式部署形态。

### 2.2 禁止混淆 SQLite 与 PostgreSQL 的职责

- SQLite 不承载调度真相
- PostgreSQL 不承载 admin 真相

### 2.3 禁止长期并存多套正式前端运行面

不允许：

- 一个正式域名长期挂两套正式前端
- 一个页面链路来自 3000，静态资源来自 3001，API 又来自第三套后端

### 2.4 禁止把测试路径当正式路径

不允许：

- 用临时验收目录冒充正式运行目录
- 用 fake TOS 目录设计生产数据流
- 用临时脚本替代正式发布规则

### 2.5 禁止在未备份前进行清洗

清洗前必须确认：

- SQLite 备份完成
- PostgreSQL 备份完成
- 当前 release 信息可回滚

## 3. 必须先更新文档的场景

如果你要修改以下内容，必须先改文档：

- 系统边界
- 部署角色
- 发布流程
- 备份流程
- 回滚流程
- A 机器与 Worker 的职责分配

## 4. 对历史错误的固定结论

历史已经证明以下做法会把系统做乱：

- 只盯着页面，不理解系统是分布式任务处理系统
- 把 A 机器当成什么都能装的万能主机
- 把当前线上临时运行面误判成目标架构
- 没有先定义数据库边界就重写前端或 API
- 没有 release manifest 就上线

## 5. 任务切换时的判断标准

如果你的任务是：

- 页面开发
- admin 修改
- 用户端交互优化

优先停留在系统知识层即可。

如果你的任务是：

- 上线
- 清洗
- 重建
- 发布
- 备份
- 恢复

必须进一步阅读重建专项层。

## 对 Agent 的直接指令

- 如果你没有读完系统定义和职责边界，就不要下部署判断。
- 如果你觉得“把服务先丢到 A 机器上跑通再说”是个好主意，请先停下，这通常是在重复历史错误。
- 任何会影响运行面、数据库边界、发布路径的改动，都必须留下文档证据。
