# 04. 发布规则

本文回答什么问题：

- 标准发布流程是什么
- 为什么不能继续混用多种发布方法
- A 机器和 Worker 机器如何保持版本一致
- 发布、验收、回滚的最小闭环是什么

## 1. 总原则

- 本地负责开发与测试
- 云上负责正式构建、正式切换、正式运行
- Git 是代码真相
- release manifest 是发布真相
- 正式 release 镜像是可选的恢复加速器，不是唯一真相

## 2. 标准发布流

### Step 1：本地完成开发

要求：

- 在独立分支开发
- 本地先完成必要测试
- 不在 A 机器线上目录里直接改代码作为主流程

### Step 2：提交并标记版本

要求：

- 提交到 Git
- 给出明确的 commit 或 tag
- 这个 tag 或 sha 是本次发布的唯一标识

### Step 3：A 机器和 Worker 机器拉同一版本

要求：

- A 与 Worker 必须拉取同一 release
- 两边 `HEAD` 必须可对齐到同一 commit 或 tag

### Step 4：云上构建

A 机器构建：

- 网站前端
- 网站业务 API
- 调度 API
- 调度 Runtime

Worker 构建：

- Worker Gateway
- Smart Cut Worker

### Step 5：发布前备份

发布脚本必须先做：

- 当前运行版本备份
- 当前数据库备份引用确认
- release manifest 生成

### Step 6：启动候选版本

要求：

- 新版本先以可验证方式启动
- 不得直接覆盖后无检查

### Step 7：健康检查与最小验收

至少验证：

- A 机器网站登录正常
- admin 正常
- 调度中心正常
- Worker 可注册、可领任务
- 一条主链路任务能跑通

### Step 8：切流

要求：

- nginx 或服务入口只指向一套正式运行面
- 切流后保留上一版回滚锚点

## 3. 为什么不再走“本地大包上传”

不推荐继续长期依赖：

- 本地 build 完整 runtime 再 `scp`
- 本地打多个大 tar 包反复上传

原因：

- 本地磁盘压力大
- 上传成本高
- 版本追踪不清晰
- 容易形成“线上代码、线上包、线上脚本三套真相”

## 4. 为什么仍然使用 Docker

Docker 的价值在于：

- 固定依赖环境
- 固定启动方式
- 降低线上环境漂移
- 提高恢复和回滚速度

问题不在 Docker 本身，而在于：

- 当前镜像治理不严
- 当前发布流程并未收敛
- 当前历史运行面长期并存

## 5. 版本治理

正式发布必须同时具备：

- git sha
- git tag 或 release id
- compose 或运行脚本版本
- image tag 或 digest
- release manifest

禁止只说：

- “最新那版”
- “线上那版”
- “A 机器当前跑的那版”

## 6. 回滚原则

回滚基于“上一版稳定 release”，不是临时热修猜测。

要求：

- 发布前先明确上一版 release id
- 回滚脚本必须能快速切回上一版镜像或运行目录
- 回滚后要立即跑健康检查

## 7. 对网站与 Worker 的发布要求

### A 机器

必须保持：

- 网站侧运行面单一
- 调度中心运行面清晰
- 不长期并存两套正式前端

### Worker 机器

必须保持：

- Gateway 与算法镜像版本对应
- 与 A 机器调度协议兼容
- 与 TOS 交互协议稳定

## 对 Agent 的直接指令

- 不要再发明新的临时发布路径。
- 如果你要改发布方式，先更新本文件，再改脚本。
- 如果你的方案无法回答“如何备份、如何验收、如何回滚”，那它就不是正式发布方案。
