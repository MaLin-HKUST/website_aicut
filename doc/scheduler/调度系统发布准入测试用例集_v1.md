# 调度系统发布准入测试用例集 v1

## 1. 文档目标

本文档用于定义任务调度系统的**发布准入测试标准**。  
目标不是“做一些测试”，而是建立一套可以作为**上线门槛**的测试用例集。

本测试集面向以下系统特征：

- A 负责写任务表，Worker 只读任务表
- Worker 负责写设备表，A 只读设备表
- 一个 Worker 一次只处理一个任务
- 调度策略为 FCFS + 能力匹配 + 空闲设备分配
- 支持单步任务、分步任务、人工后处理任务
- 支持用户离开页面后的 72 小时内恢复
- 用户放弃时删除 workspace
- 异常以报警日志为主，不做复杂自动恢复

---

## 2. 发布准入标准

### 2.1 风险等级定义

- **P0 / 阻断级**：只要有 1 条失败，禁止上线
- **P1 / 关键级**：原则上必须全部通过，除非明确降级某个功能
- **P2 / 加固级**：用于稳定性和回归增强，建议在正式对外前补齐

### 2.2 上线通过标准

系统必须满足以下条件，才允许上线：

1. 全部 **P0** 用例 100% 通过
2. 全部 **P1** 用例 100% 通过
3. 所有状态路径断言通过
4. 所有副作用断言通过
5. 所有报警日志断言通过

### 2.3 总原则

只要存在任意一条测试用例，能够证明系统会破坏以下任一项，就不允许上线：

- 状态机闭环
- 调度唯一性
- 任务与设备职责边界
- workspace 生命周期
- 用户恢复/放弃逻辑
- 异常可见性

---

## 3. 测试范围总览

本测试集共覆盖 8 个测试域：

- A. 任务状态机合法性
- B. 设备状态机合法性
- C. 任务表与设备表联动
- D. 调度正确性
- E. 主业务闭环
- F. 用户离开、恢复、放弃、超时
- G. 异常与失败处理
- H. 幂等性与边界行为

# A. 任务状态机合法性（11 个）

## P0-TASK-001：任务创建后进入 pending
- **等级**：P0
- **测试目标**：验证用户创建任务后，任务初始状态必须为 `pending`
- **前置条件**：系统正常；用户可创建任务
- **操作步骤**：
  1. 用户从前端创建一个新任务
  2. A 接收请求并写入任务表
- **预期结果**：
  - 任务表新增一条记录
  - 任务状态为 `pending`
- **关键断言**：
  - 不允许直接进入 `assigned` / `running`
  - 任务 ID 唯一
  - `created_at` 已写入

## P0-TASK-002：pending 可进入 assigned
- **等级**：P0
- **测试目标**：验证 A 可以将 `pending` 任务推进到 `assigned`
- **前置条件**：存在 `pending` 任务；存在兼容且 `idle` 的 Worker
- **操作步骤**：
  1. A 扫描待调度任务
  2. A 选择兼容 Worker
  3. A 写入 `assigned_worker_id`
  4. A 将任务状态改为 `assigned`
- **预期结果**：
  - 任务状态变为 `assigned`
- **关键断言**：
  - `assigned_worker_id` 已写入
  - 不允许跳过 `assigned` 直接到 `running`

## P0-TASK-003：assigned 可进入 running
- **等级**：P0
- **测试目标**：验证任务只有在 Worker 真正运行后，A 才将任务改为 `running`
- **前置条件**：任务状态 `assigned`；对应 Worker 已被分配
- **操作步骤**：
  1. Worker 轮询任务表
  2. Worker 进入设备 `assign`
  3. Worker 进入设备 `running`
  4. A 观察到设备 `running`
  5. A 将任务改为 `running`
- **预期结果**：
  - 任务状态改为 `running`
- **关键断言**：
  - A 不能在 Worker 未进入 `running` 前提前写任务 `running`

## P0-TASK-004：running 可进入 waiting_user
- **等级**：P0
- **测试目标**：验证分步任务中，某一步完成后可进入 `waiting_user`
- **前置条件**：任务为分步任务；当前处于 `running`
- **操作步骤**：
  1. Worker 完成当前步骤
  2. A 判断后续仍需用户确认
  3. A 将任务改为 `waiting_user`
- **预期结果**：
  - 任务状态为 `waiting_user`
- **关键断言**：
  - 不应直接 `finished`
  - 应释放 Worker

## P0-TASK-005：running 可进入 post
- **等级**：P0
- **测试目标**：验证任务在机器执行完成后可进入 `post`
- **前置条件**：任务处于 `running`；该任务需要人工后处理
- **操作步骤**：
  1. Worker 完成执行
  2. Worker 设备状态变 `post`
  3. A 观察到设备 `post`
  4. A 将任务状态改为 `post`
- **预期结果**：
  - 任务状态变为 `post`
- **关键断言**：
  - 进入 `post` 前必须先有设备 `post`

## P0-TASK-006：running 可进入 finished
- **等级**：P0
- **测试目标**：验证无需人工后处理的任务可从 `running` 结束到 `finished`
- **前置条件**：任务处于 `running`；该任务为最后一步且无需 post
- **操作步骤**：
  1. Worker 执行完成
  2. Worker 设备状态变 `post`
  3. A 识别无需人工后处理
  4. A 将任务改为 `finished`
- **预期结果**：
  - 任务状态为 `finished`
- **关键断言**：
  - 不应错误停留在 `post`

## P0-TASK-007：running 可进入 failed
- **等级**：P0
- **测试目标**：验证执行失败时任务进入 `failed`
- **前置条件**：任务处于 `running`
- **操作步骤**：
  1. Worker 执行时报错
  2. Worker 设备状态改为 `error`
  3. A 观察到设备 `error`
  4. A 将任务改为 `failed`
- **预期结果**：
  - 任务状态为 `failed`
- **关键断言**：
  - 不应停留在 `running`

## P0-TASK-008：waiting_user 可进入 suspended
- **等级**：P0
- **测试目标**：验证等待用户超时或用户离开后，任务可进入 `suspended`
- **前置条件**：任务状态 `waiting_user`
- **操作步骤**：
  1. 用户离开页面或等待超时
  2. A 将任务改为 `suspended`
- **预期结果**：
  - 任务状态为 `suspended`
- **关键断言**：
  - `keep_until` 已正确设置

## P0-TASK-009：suspended 可恢复到 assigned
- **等级**：P0
- **测试目标**：验证挂起任务可在 72 小时内恢复并重新进入调度
- **前置条件**：任务状态 `suspended`；未超过 72 小时；有兼容 Worker
- **操作步骤**：
  1. 用户进入页面并点击继续
  2. A 将任务重新送入调度
  3. A 分配 Worker
  4. 任务进入 `assigned`
- **预期结果**：
  - 任务状态变为 `assigned`
- **关键断言**：
  - 使用原 workspace
  - 不创建新 task

## P0-TASK-010：suspended 可进入 abandoned
- **等级**：P0
- **测试目标**：验证用户点击放弃时，挂起任务进入 `abandoned`
- **前置条件**：任务状态 `suspended`
- **操作步骤**：
  1. 用户再次进入页面
  2. 系统提示是否继续
  3. 用户点击放弃
  4. A 将任务改为 `abandoned`
- **预期结果**：
  - 任务状态为 `abandoned`
- **关键断言**：
  - workspace 被删除

## P0-TASK-011：suspended 超时进入 timeout_closed
- **等级**：P0
- **测试目标**：验证挂起任务超过 72 小时后自动关闭
- **前置条件**：任务状态 `suspended`
- **操作步骤**：
  1. 系统时间推进超过 72 小时
  2. A 扫描超时任务
  3. A 将任务改为 `timeout_closed`
- **预期结果**：
  - 任务状态为 `timeout_closed`
- **关键断言**：
  - workspace 被清理
  - 不再允许恢复

# B. 设备状态机合法性（6 个）

## P0-DEV-001：idle 可进入 assign
- **等级**：P0
- **测试目标**：验证 Worker 看到分配给自己的任务后可进入 `assign`
- **前置条件**：Worker 状态 `idle`；任务已分配给该 Worker
- **操作步骤**：
  1. Worker 轮询任务表
  2. Worker 发现任务属于自己
  3. Worker 将设备状态改为 `assign`
- **预期结果**：
  - 设备状态为 `assign`
- **关键断言**：
  - `current_task_id` 已写入

## P0-DEV-002：assign 可进入 running
- **等级**：P0
- **测试目标**：验证 Worker 准备完成后可进入 `running`
- **前置条件**：设备状态 `assign`
- **操作步骤**：
  1. Worker 拉取数据并完成准备
  2. Worker 开始执行
  3. Worker 将设备状态改为 `running`
- **预期结果**：
  - 设备状态为 `running`
- **关键断言**：
  - 不允许卡在 `assign` 但已经实际执行

## P0-DEV-003：running 可进入 post
- **等级**：P0
- **测试目标**：验证 Worker 执行完成后可进入 `post`
- **前置条件**：设备状态 `running`
- **操作步骤**：
  1. Worker 执行完成
  2. Worker 上传结果
  3. Worker 将设备状态改为 `post`
- **预期结果**：
  - 设备状态为 `post`

## P0-DEV-004：running 可进入 error
- **等级**：P0
- **测试目标**：验证 Worker 执行失败时可进入 `error`
- **前置条件**：设备状态 `running`
- **操作步骤**：
  1. Worker 执行报错
  2. Worker 将设备状态改为 `error`
- **预期结果**：
  - 设备状态为 `error`

## P0-DEV-005：post 可回 idle
- **等级**：P0
- **测试目标**：验证 A 已将任务状态推进后，Worker 可从 `post` 释放回 `idle`
- **前置条件**：设备状态 `post`；A 已将任务改为 `post` 或 `finished`
- **操作步骤**：
  1. A 完成任务表推进
  2. Worker 检测到可释放
  3. Worker 将设备状态改为 `idle`
- **预期结果**：
  - 设备状态为 `idle`
- **关键断言**：
  - 不允许 A 还未推进任务表时就提前回 `idle`

## P0-DEV-006：error 可回 idle
- **等级**：P0
- **测试目标**：验证设备出错记录完成后可释放回 `idle`
- **前置条件**：设备状态 `error`
- **操作步骤**：
  1. A 已处理任务失败逻辑
  2. Worker 释放当前任务上下文
  3. Worker 将设备状态改为 `idle`
- **预期结果**：
  - 设备状态为 `idle`

# C. 任务表与设备表联动（9 个）

## P0-LINK-001：A 先写 assigned，Worker 才能接单
- **等级**：P0
- **测试目标**：验证接单前提是任务已被 A 分配
- **前置条件**：存在 pending 任务
- **操作步骤**：
  1. 不进行 A 分配
  2. 观察 Worker 是否会接单
- **预期结果**：
  - Worker 不应接单
- **关键断言**：
  - 没有 `assigned_worker_id` 时，Worker 不应进入 `assign`

## P0-LINK-002：Worker 改 assign 不应修改任务表
- **等级**：P0
- **测试目标**：验证 Worker 只写设备表，不写任务表
- **前置条件**：任务状态 `assigned`
- **操作步骤**：
  1. Worker 接单
  2. Worker 将设备状态改为 `assign`
- **预期结果**：
  - 任务表状态仍为 `assigned`
- **关键断言**：
  - Worker 不得把任务改成 `running`

## P0-LINK-003：Worker 进入 running 后，A 才写任务 running
- **等级**：P0
- **测试目标**：验证任务 `running` 由 A 观察设备状态后推进
- **前置条件**：任务 `assigned`；设备可执行
- **操作步骤**：
  1. Worker 进入 `running`
  2. A 读取设备状态
  3. A 写任务 `running`
- **预期结果**：
  - 状态顺序正确
- **关键断言**：
  - 不能出现任务先于设备进入 `running`

## P0-LINK-004：Worker 进入 post 后，A 才写任务 post/finished
- **等级**：P0
- **测试目标**：验证任务完成推进必须晚于设备 `post`
- **前置条件**：设备 `running`
- **操作步骤**：
  1. Worker 执行完成并进入 `post`
  2. A 观察到设备 `post`
  3. A 推进任务到 `post` 或 `finished`
- **预期结果**：
  - 状态顺序正确

## P0-LINK-005：A 推进任务后，Worker 才能回 idle
- **等级**：P0
- **测试目标**：验证 Worker 回 `idle` 的时机正确
- **前置条件**：设备 `post`
- **操作步骤**：
  1. Worker 进入 `post`
  2. A 还未推进任务表
  3. 检查 Worker 是否提前回 `idle`
  4. A 推进任务表
  5. Worker 回 `idle`
- **预期结果**：
  - Worker 只在 A 推进后回 `idle`

## P0-LINK-006：Worker 不得直接改任务表
- **等级**：P0
- **测试目标**：验证职责边界
- **前置条件**：存在被分配任务
- **操作步骤**：
  1. Worker 正常接单、执行、完成
  2. 监控任务表写入来源
- **预期结果**：
  - 任务表所有状态变更均来自 A
- **关键断言**：
  - Worker 无直接写权限或无实际写行为

## P0-LINK-007：A 不得直接改设备表
- **等级**：P0
- **测试目标**：验证职责边界
- **前置条件**：存在 Worker 设备行
- **操作步骤**：
  1. A 完成任务调度和推进
  2. 监控设备表写入来源
- **预期结果**：
  - 设备表状态变更均来自 Worker

## P0-LINK-008：assigned_worker_id 与 current_task_id 保持一致
- **等级**：P0
- **测试目标**：验证分配关系一致
- **前置条件**：任务已分配；Worker 已接单
- **操作步骤**：
  1. A 给某任务分配 WorkerX
  2. WorkerX 接单
- **预期结果**：
  - 任务表 `assigned_worker_id == WorkerX`
  - 设备表 `current_task_id` 指向该任务
- **关键断言**：
  - 不允许交叉错配

## P0-LINK-009：一个 Worker 同时最多一个当前任务
- **等级**：P0
- **测试目标**：验证单 Worker 单任务约束
- **前置条件**：某 Worker 已持有任务
- **操作步骤**：
  1. A 再尝试给该 Worker 分配第二个任务
- **预期结果**：
  - 第二个任务不应分配成功
- **关键断言**：
  - Worker 不应同时存在两个活动任务上下文

# D. 调度正确性（9 个）

## P0-SCH-001：单任务单 Worker 正常调度
- **等级**：P0
- **测试目标**：验证最基本调度链路
- **前置条件**：1 个 pending 任务；1 个兼容 idle Worker
- **操作步骤**：
  1. A 调度
- **预期结果**：
  - 任务被分配给该 Worker

## P0-SCH-002：多任务单 Worker 按 FCFS
- **等级**：P0
- **测试目标**：验证先来先服务
- **前置条件**：2 个同类型 pending 任务；1 个兼容 idle Worker
- **操作步骤**：
  1. A 调度第一个任务
  2. 等第一个完成后
  3. A 调度第二个任务
- **预期结果**：
  - 先创建的任务先执行

## P1-SCH-003：多任务多 Worker 时，队首任务优先
- **等级**：P1
- **测试目标**：验证 FCFS 在并行环境下仍成立
- **前置条件**：多个 pending 任务；多个 idle Worker
- **操作步骤**：
  1. A 扫描任务并调度
- **预期结果**：
  - 队列更前面的任务先获得资源

## P0-SCH-004：不兼容任务不能分给该 Worker
- **等级**：P0
- **测试目标**：验证能力匹配约束
- **前置条件**：任务类型 A；某 Worker 不支持类型 A
- **操作步骤**：
  1. A 扫描设备表
  2. 尝试分配
- **预期结果**：
  - 该 Worker 不会被分配此任务

## P0-SCH-005：全部兼容 Worker 忙时，任务保持等待
- **等级**：P0
- **测试目标**：验证忙碌时不乱分配
- **前置条件**：存在兼容任务；所有兼容 Worker 非 idle
- **操作步骤**：
  1. A 调度
- **预期结果**：
  - 任务保持未分配
- **关键断言**：
  - 不应分给 busy Worker

## P1-SCH-006：有空闲兼容 Worker 时，等待任务可被分配
- **等级**：P1
- **测试目标**：验证空闲资源释放后可继续调度
- **前置条件**：任务待执行；某兼容 Worker 由 busy 变 idle
- **操作步骤**：
  1. A 周期性调度
- **预期结果**：
  - 任务被分配给该 Worker

## P1-SCH-007：多个兼容 idle Worker 时，分配行为符合既定规则
- **等级**：P1
- **测试目标**：验证多候选设备下分配策略稳定
- **前置条件**：存在多个兼容 idle Worker
- **操作步骤**：
  1. A 调度
- **预期结果**：
  - 分配给符合当前规则的某一台 Worker
- **关键断言**：
  - 规则必须稳定、可预测

## P0-SCH-008：非 idle Worker 不得再次被分配
- **等级**：P0
- **测试目标**：验证忙碌设备不可重复分配
- **前置条件**：某 Worker 状态为 assign / running / post / error
- **操作步骤**：
  1. A 调度新任务
- **预期结果**：
  - 不会分配给该 Worker

## P1-SCH-009：恢复任务允许由新 Worker 接续
- **等级**：P1
- **测试目标**：验证恢复时不要求原 Worker
- **前置条件**：任务 `suspended`；原 Worker 不可用；另一兼容 Worker idle
- **操作步骤**：
  1. 用户点击继续
  2. A 调度
- **预期结果**：
  - 任务可分配给新 Worker
- **关键断言**：
  - workspace 仍可沿用

# E. 主业务闭环（6 个）

## P0-BIZ-001：单步任务自动完成闭环
- **等级**：P0

## 5. 测试执行建议

建议按以下顺序执行：

1. A 域：任务状态机
2. B 域：设备状态机
3. C 域：双表联动
4. D 域：调度正确性
5. E 域：主业务闭环

- 所有 **P0** 100% 通过
- 所有 **P1** 100% 通过
- 若 P2 未通过，不建议正式对外，但可作为后续加固项视情况处理

### 5.3 测试结果记录建议
每条测试用例执行后，至少记录：

- 执行时间
- 执行版本
- 执行人
- 是否通过
- 失败截图/日志
- 失败原因
- 是否阻断上线

## 6. 最终结论

这 66 个测试用例构成了当前版本调度系统的**发布准入测试集**。  
在当前业务边界下，只要系统能够：

- 通过全部 P0

- 且所有状态路径、资源副作用、报警日志断言都正确

则可以认为这套调度系统已经达到**可上线标准**。

如果任意一条阻断级或关键级测试未通过，则代码必须继续修改，直到通过为止。
