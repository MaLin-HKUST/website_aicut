# PROJECT_RULES.md

## 1. 文档目的

本文件用于定义本项目的统一开发规则。  
目标不是描述产品做什么，而是规定：

- 项目统一使用什么技术栈
- 前后端代码如何组织
- 命名如何统一
- 状态如何统一
- 权限如何统一
- 文档如何同步更新
- Git 如何提交
- AI coding agent 应该如何在本项目中工作

本文件优先级高于零散口头约定。  
如果后续产品需求变化，应先更新 `PRODUCT_PRD.md`，再同步修订本文件。

---

## 2. 项目原则

本项目遵循以下原则：

### 2.1 小步迭代原则
- 允许逐功能上线部署
- 每次只开发一个或少量功能闭环
- 每次迭代后再决定下一轮细节
- 不要求一开始就设计完整终局架构

### 2.2 文档先行原则
- 新功能开发前，必须先确认相关文档
- 文档不是事后补充，而是开发输入的一部分
- 如果实现与文档冲突，应先修正文档，再继续开发

### 2.3 代码与文档同步原则
以下变更必须同步更新文档：
- 新增页面
- 新增任务状态
- 新增接口
- 新增任务类型
- 修改权限
- 修改上传 / 执行 / 重试流程
- 修改数据库字段

### 2.4 Git 留痕原则
- 所有开发必须通过 Git 提交记录
- 禁止把多个不相关功能混在一次提交里
- 提交信息必须能说明功能点

### 2.5 简化优先原则
- 第一阶段优先实现最小闭环
- 能简单做的，不先引入复杂方案
- 不为未来可能用到的复杂场景过度设计

## 3. 技术栈规则

### 3.1 前端
统一使用：

- Next.js
- TypeScript
- Tailwind CSS
- shadcn/ui
- React Hook Form
- Zod（用于表单与数据校验）
- TanStack Query 或等价方案（用于服务端数据获取与缓存）

规则：
- 不使用 jQuery
- 不使用多套 UI 体系混搭
- 页面组件优先保持简洁、后台管理风格
- 所有前端类型定义必须使用 TypeScript

---

### 3.2 后端
统一使用：

- FastAPI
- Python 3.11+
- Pydantic
- SQLAlchemy / SQLModel（二选一，项目内保持统一）
- PostgreSQL

规则：
- 所有接口必须有明确的请求模型和响应模型
- 所有枚举类必须集中定义
- 不允许在路由里直接写大段业务逻辑
- 路由层、服务层、数据层分离

---

### 3.3 任务执行
统一使用：

- Python 独立 worker
- 数据库轮询待执行任务
- 本地文件目录执行视频处理
- 本地生成结果后上传 TOS

规则：
- 第一阶段不引入复杂消息队列系统
- 第一阶段不引入 Celery 作为强依赖
- worker 必须支持心跳更新
- worker 必须支持任务失败回写
- worker 必须支持管理员终止运行中任务

---

### 3.4 存储
统一使用：

- TOS：上传原始输入文件与结果输出文件
- 本地磁盘：任务执行工作目录与系统预设素材目录

规则：
- 用户输入文件优先走 TOS
- 系统预设素材优先放服务器本地
- 本地任务目录与系统预设目录必须分离
- 不允许直接把大文件通过 API 服务中转上传

---

### 3.5 部署
第一阶段推荐部署方式：

- 前端：Vercel 或等价前端托管
- 后端 API：自有服务器 / Docker
- Worker：自有服务器 / Docker
- 数据库：PostgreSQL
- 反向代理：Nginx
- 统一使用 Docker Compose 组织本地或测试环境

规则：
- 生产环境部署方式必须能支撑独立重启 worker
- 前端与后端应独立部署
- worker 不应与 API 进程混在同一运行进程中
